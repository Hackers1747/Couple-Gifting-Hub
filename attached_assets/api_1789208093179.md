# API Reference

Base path: `/api` (mounted in `artifacts/api-server/src/app.ts`). All routers are
registered in `artifacts/api-server/src/routes/index.ts`. Storage for every route
below is **in-memory** (see [architecture.md](./architecture.md)) unless noted.

> Only `GET /api/healthz` is present in the OpenAPI spec
> (`lib/api-spec/openapi.yaml`). Everything else below was written directly in
> the Express routers and is documented here from source, not from the spec.

## Health — `routes/health.ts`

- `GET /api/healthz` → `{ status: "ok" }`, validated with the generated
  `HealthCheckResponse` Zod schema from `@workspace/api-zod`.

## Cards — `routes/cards.ts`

- `GET /api/cards` → `{ cards: [] }` (stub, always empty).
- `POST /api/cards` → creates a token as `` `${experience}-${random}` `` and
  returns `{ token, message }`. Does not persist the submitted card body.
- `GET /api/cards/slug/:slug` and `GET /api/cards/:id` → both return a
  **mocked** card (`mockCard()`), not the card that was actually created by
  `POST /api/cards`. The mock is keyed off whichever experience name prefixes
  the slug (e.g. `sorry-abc123` → the "sorry" mock), always attributed to
  sender "Rohan" / recipient "Priya", with fixed sample `storyMemories`.
- `PATCH /api/cards/:id` / `DELETE /api/cards/:id` → stub acknowledgements only,
  no actual update/delete logic.

**Gap:** because `POST` doesn't persist and `GET` returns canned data, the create
→ view round-trip is not functionally wired end-to-end yet.

## Payment — `routes/payment.ts`

Razorpay integration. Plan amounts (paise): `per_card` 17900 (₹179), `monthly`
29900 (₹299), `annual` 199900 (₹1,999) — must match `PLANS` in
`artifacts/heartdrop/src/pages/Payment.tsx`.

- `POST /api/payment/create-order` — body `{ cardId, planType }`. Creates a
  Razorpay order via `razorpay.orders.create`, stores the pending payment in an
  in-memory `payments` map keyed by Razorpay order id.
- `POST /api/payment/verify` — body includes `razorpayOrderId`,
  `razorpayPaymentId`, `razorpaySignature`, `cardId`, `planType`, `senderName`,
  `recipientName`. Verifies the HMAC-SHA256 signature against
  `RAZORPAY_KEY_SECRET`; on success marks the in-memory payment `"paid"` and
  returns a fresh `shareToken` + `shareUrl` (`heartdrop.in/card/:shareToken`).
  **Note:** this generates a new share token independent of the `cardId` /
  `POST /api/cards` token — the two are not currently linked.
- `GET /api/payment/status/:orderId` — looks up the in-memory payment record;
  404 if not found.

## AI — `routes/ai.ts`

Uses `@google/genai` with `gemini-2.5-flash` when `GEMINI_API_KEY` is set;
otherwise every endpoint falls back to canned template messages
(`FALLBACK_MESSAGES`) so the app functions without the key.

- `POST /api/ai/message` — canonical endpoint per the intended spec (also
  called internally by `cron.ts`'s monthly Love Drop job).
- `POST /api/ai/generate-message` — identical logic to `/message`; kept because
  the frontend (`Create.tsx` Step 4) calls this legacy name.
- `POST /api/ai/suggest-experience` — given `{ occasion, notes }`, asks Gemini
  to pick one of the 7 experience types; falls back to `"anniversary"` if no
  API key or on any parse failure.

All three require `experience`, `recipientName`, `senderName` (message/generate
routes) — 400 if missing.

## Tracking — `routes/track.ts`

- `POST /api/track` — body `{ cardId, eventType, emojiReaction?, senderWhatsapp?,
  recipientName?, experience? }`. Appends to an in-memory `events` array and
  upserts an in-memory `cardRegistry` entry if metadata is supplied. On
  `eventType: "opened"` or `"reacted"`, fires a WhatsApp notification to the
  card's registered sender via `sendWhatsApp` (fire-and-forget).
- `POST /api/track/open/:cardId` — legacy alias, logs an `"opened"` event only.
- `GET /api/track/analytics/:cardId` — aggregates the in-memory events for a
  card: open count, reaction counts by emoji, watermark-click count, last-open
  timestamp.
- `POST /api/track/register` — registers `{ cardId, recipientName, experience,
  senderWhatsapp }` in `cardRegistry`; called after payment verification so
  later `opened`/`reacted` events know who to notify.

`cardRegistry` is pre-seeded with 7 demo slugs (`sorry-demo`, `proposal-demo`,
etc., all recipient "Priya") so tracking works against the front-end's demo
cards without a real create flow.

## WhatsApp — `routes/whatsapp.ts`

`sendWhatsApp(to, message)` (exported, used by `cron.ts` and `track.ts`) normalizes
the phone number to a `91`-prefixed E.164-ish string, then:
- If `WHATSAPP_PHONE_ID` and `WHATSAPP_ACCESS_TOKEN` are both set, sends via the
  Meta Cloud API (`graph.facebook.com/v18.0/{phoneId}/messages`).
- Otherwise, logs `[WhatsApp stub] → ...` to the console and returns `{ stub:
  true, to: phone }` — no real message is sent.

- `POST /api/whatsapp/send` — body `{ to, message }`, calls `sendWhatsApp`
  directly.
- `POST /api/whatsapp/webhook` — logs the incoming body and returns `{ ok: true
  }`. No signature/verification-token validation implemented, and no handling
  of Meta's webhook verification `GET` handshake (`hub.challenge`) — only `POST`
  is defined.
